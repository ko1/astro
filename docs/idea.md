# ASTro: AST-Based Reusable Optimization Framework — 核心アイデア

著者: 笹田耕一 (ko1@st.inc, STORES株式会社)

論文:
- VMIL 2025: "ASTro: An AST-Based Reusable Optimization Framework"
- PPL 2026: "ASTro による JIT コンパイラの試作"

本書は ASTro の **本質的なアイディアだけ** を説明する。
応用・各論はトピック別の `idea_*.md` に分割してある（[§4 ドキュメントマップ](#4-ドキュメントマップ)）。

## 1. 問題意識

高性能なインタプリタを作るには、一般的に以下の段階を経る:

1. AST を構築し、木を辿るインタプリタで実行（簡単だが遅い）
2. バイトコード VM を作る（性能向上するが開発コスト大）
3. JIT コンパイラを追加（さらに高速だが複雑）

各段階で VM の設計・JIT バックエンドなど言語ごとに専用の実装が必要。
Truffle/Graal や RPython は高性能だが、重量級ツールチェインに依存し、ポータビリティやデバッグ性に難がある。

ASTro は「**AST インタプリタを一度書けば、部分評価によって高品質なネイティブコードまで自動で到達できる**」枠組みを、C コンパイラという成熟した基盤の上に軽量に実現する。

## 2. 核心アイデア

ASTro の本質は次の 5 点に集約される:

1. **`node.def` に定義を書く** — ノードの評価ロジックを一度だけ C で書く
2. **その定義から specializer（部分評価器）を自動生成する** — ASTroGen がインタプリタと部分評価器の両方を生成する
3. **specializer は dispatcher を特化するだけで、AST から高品質なネイティブコードが得られる** — エバリュエータは無変更のまま、C コンパイラがインライン展開する
4. **各特化コードは Merkle ハッシュによってプロセスを超えて一意に特定できる** — 構造がそのままコードの ID になる
5. **実行時データをハッシュに含めれば、それを焼き込んだネイティブコードも同じ枠組みで一意に特定できる** — プロファイル情報の焼き込みも同一機構で扱える

JIT コンパイラ（[idea_jit.md](./idea_jit.md)）などは、この枠組みの **応用** である。

### 2.1 node.def — 定義は一度だけ書く

ユーザ（言語実装者）が書くのは、各 AST ノードの評価ロジック（EVAL body）を C コードで記述した `node.def` だけ:

```c
NODE_DEF
node_add(CTX *c, NODE *n, NODE *lhs, NODE *rhs)
{
    return EVAL_ARG(c, lhs) + EVAL_ARG(c, rhs);
}
```

ASTroGen (`lib/astrogen.rb`) がここから、木を辿るインタプリタ・部分評価器・ハッシュ関数・アロケータ等の C コードを一式自動生成する。VM 設計もバイトコードも JIT バックエンドも書かない。
生成物の詳細は [idea_astrogen.md](./idea_astrogen.md)、書き方の実践は [usage.md](./usage.md)。

### 2.2 部分評価 + C コンパイラ

- インタプリタの **部分評価 (Partial Evaluation)** の結果を **C のソースコード** として出力する
- 第一二村射影: インタプリタ I をプログラム P に対して部分評価すると、P の残余プログラム PE(I, P) が得られる
- 残余プログラムを汎用の C コンパイラ（gcc, clang 等）でコンパイルすることで、高品質なネイティブコードを得る
- C コンパイラは成熟した最適化基盤であり、新たなバックエンド開発が不要

### 2.3 specializer は dispatcher を特化するだけ

ASTro の最も重要な設計判断は **ディスパッチャとエバリュエータの分離**:

- **エバリュエータ (EVAL_xxx)**: ノードの評価ロジック本体。ユーザが `node.def` に記述
- **ディスパッチャ (DISPATCH_xxx)**: ノードのフィールドを取り出してエバリュエータに渡す薄い関数。ASTroGen が自動生成

この分離により:

- 部分評価は **ディスパッチャだけを特化** すれば良い（エバリュエータは変更不要）
- 特化ディスパッチャ（SD）は子の特化ディスパッチャを **具体的な関数名** で呼ぶため、C コンパイラがインライン展開できる
- ユーザ定義のエバリュエータに一切手を加えずに、AST 全体が 1 つの最適化されたネイティブコードに溶け合う

例: `1 + 2 * 3` の AST を特化すると、最外部のディスパッチャは `mov $0x7, %eax; ret` にまでインライン化される。

見落とされがちだが重要なメリットとして、**ASTroGen は C パーサを持たずに部分評価器を作れる**。EVAL body は不透明なテキストとして `node_eval.c` にそのまま転写されるだけで、ASTroGen が解析するのは `NODE_DEF` のシグネチャ 1 行だけ。specializer が生成するのも「オペランドを定数化し、子を具体的な関数名で呼ぶディスパッチャ」という定型コードに過ぎない。C コードの意味解析・インライン展開・定数畳み込みはすべて C コンパイラの仕事であり、ASTroGen 自身は C を理解しないまま「C で書かれたインタプリタの部分評価」が成立する。「EVAL body を一切書き換えない（C パーサを書かない）」はフレームワークの根本方針として拡張時にも貫かれている（[idea_variadic.md](./idea_variadic.md) §2）。

### 2.4 Merkle ツリーハッシュ — 構造がコードの ID になる

- 各 AST ノードに Merkle ツリーハッシュを付与する
- ハッシュは (ノードの種類, 各属性のハッシュ) から計算（子ノードは再帰的）
- 特化ディスパッチャの関数名は `SD_<hash>` 形式
- 同一構造の部分木は同一ハッシュ → コンパイル済みコードを **プロセス間・マシン間で共有・再利用できる**

つまりコンパイル結果は「あの実行でコンパイルしたもの」ではなく「このハッシュのコード」として content-addressable に管理される。コンパイルキャッシュ・AOT・分散コンパイルがすべてこの性質の上に乗る。
保存・ロードの実装は [idea_code_store.md](./idea_code_store.md)。

### 2.5 実行時データの焼き込みも同じ枠組みで (Horg / Hopt)

構造だけから計算するハッシュ **Horg** に対し、実行時に得たデータ（インラインキャッシュの中身などのプロファイル情報）を **ハッシュ計算に混ぜた** ものが **Hopt**:

- 実行時データを定数として焼き込んだ特化コードも `SD_<Hopt>` として一意に特定できる
- 同じ構造 (Horg) でもプロファイルが異なれば別の Hopt → 別のコード、として自然に区別される
- Horg と同様にプロセスを超えて再利用できる: 1 回目の実行でプロファイルを採り、2 回目以降は焼き込み済みコードをロードするだけ（Profile-Guided Compilation）

「実行時情報による特化」という JIT の専売特許だったものが、ハッシュをひとつ増やすだけで AOT 的なキャッシュ機構に載る、というのがこのアイディアの肝。

## 3. 応用: 4 つの利用モード

同じ `node.def`・同じ生成基盤で、以下の 4 モードがすべて動く。違いは「いつ compile し、いつ hash → SD を解決するか」だけ:

| モード | 概要 |
|---|---|
| Plain Interpreter | 部分評価を使わず、DISPATCH → EVAL の木巡回インタプリタとして実行。`node.def` さえあれば動く最もシンプルな形態 |
| AOT Compiler | パース後に AST を特化 → C コンパイル。次回起動時に Horg でロード |
| Profile-Guided (PG) | 1 回目の実行でプロファイル収集、2 回目以降 Hopt で焼き込み済みコードをロード |
| JIT Compiler | 実行中に C コンパイラを呼び、特化コードを動的ロード。階層型キャッシュ (L0/L1/L2) でハッシュをキーにコードを共有 |

評価結果（naruby ベンチマーク）は [idea_evaluation.md](./idea_evaluation.md)。
