# ASTro 全体レビュー (2026-05-21 時点、 @child 全面導入後)

iter 58 (@child 全面導入 + callee_sp aliasing fix) 直後の状態で、
コードベース全体を見て **問題点** と **性能向上案** を整理する。
内容は baruby_precise / baruby を中心に、 framework (lib/astrogen.rb)
にも踏み込む。

## A. 問題点 (priority 順)

### A1. cons_list libgc +16% 単独退化 [P1: 数値要追跡]

iter 58 で他 bench は 5〜15% 改善した中、 cons_list だけ libgc 限定で
退化:

| bench | iter 53 baseline | iter 58 | Δ |
|-------|---:|---:|---|
| cons_list (libgc) | 0.76s | 0.88s | **+16%** |
| cons_list (copy) | 0.74s | 0.67s | -9% |
| cons_list (immix_gen) | 0.68s | 0.67s | ±0% |

precise 系では問題なし、 libgc のみ。 cons_list は `cons cell = [val,
next]` の連結リスト。 2-element BaArray の per-iter 大量 alloc。

仮説:
1. `ary_lit_2 @child` 化で alloc 回数 / GC 発火頻度が増えた
2. C-local snapshot で gcc が ary_new_from 呼び出しの inlining 判断を
   変えた結果、 hot path で icache miss / register pressure 増
3. libgc の conservative scan が `_c0` / `_c1` 経由で多くの偽 root を
   保持 → heap が肥大 → scan cost 増

要 `perf record -g ./baruby bench/cons_list.ba.rb` + flamegraph 解析。

### A2. callee_sp safety guard が冗長 [P2: 確認後撤去]

`node_call`, `node_call2`, `sp_dispatch_via_fp` で:

```c
VALUE *callee_sp = callee_fp + locals_cnt;
if (callee_sp < sp + 4) callee_sp = sp + 4;
```

parser fix (`body_locals = max_cnt`) で本来は不要。 cmp + cmov 命令を
hot path から消せる。 全 bench で oracle を再計測して safety guard
無しでも全 pass を確認後、 削除。

### A3. node_lset @child 化できなかった (機構の不完全さ) [P1: 設計検討]

@child の snapshot 場所は `sp[i]` (precise) / `_ci` (libgc) で固定。
arg-eval 用の lset chain (parser が `node_call(>3-arg)` で emit) が:

```c
lset(arg_idx + 0, g_node)   // fp[arg_idx + 0] = g
lset(arg_idx + 1, w_node)   // fp[arg_idx + 1] = w
lset(arg_idx + 2, h_node)   // fp[arg_idx + 2] = h
lset(arg_idx + 3, sub_node) // fp[arg_idx + 3] = ...
```

各 lset を @child 化すると DISPATCH が sp[0] にスピル → EVAL が
fp[index] = sp[0] と書く。 連続する lset の DISPATCH が sp[0] を上書き
する瞬間に、 直前の lset destination (fp[arg_idx+0] が caller's sp[0]
と物理的に一致するケース) を破壊する。

#### 設計選択肢

**(a) `@child` operand に "snapshot 位置" を per-operand で指定可能に**

例: `VALUE v@child(slot=lset_dest)` — snapshot 先を operand 自身の
destination にする。 lset の場合 fp[index] そのものを「snapshot
slot」 として再利用。

ASTroGen extension:
```ruby
@child = name.match(/@child(?:\(([^)]+)\))?/)
# slot 指定があれば sp[i] でなく custom expr に
```

Pro: lset で snapshot を再利用 → 連続 lset でも互いに干渉せず、 1 store
削減。
Con: framework の汎用性が下がる。 lset 専用の特殊ケース感。

**(b) lset を 2 種類に分ける**

- `node_lset_lvar` (caller の local 変数への assign、 fp[lvar_index] —
  caller_locals_cnt 未満 = 安全): @child 可。
- `node_lset_arg` (call arg slot への assign、 fp[arg_idx + i] = caller's
  sp[i] と alias 可能): NOT @child、 EVAL_ARG で取得。

Pro: 一般 lvar assign は @child でき、 SD inline で次の SD に register
渡しできる。
Con: parser に 2 ノード使い分けロジック追加。

**(c) 現状維持 (lset 全部 EVAL_ARG)**

シンプルだが lvar assign の hot path で snapshot を活用できない。 `x =
expr` の `expr` が複雑な式 (binop など) のとき、 expr の @child snapshot
を読んで fp[lvar_idx] に書く流れに 1 拍ある (現状 EVAL_ARG が 1 cmd
で済むので大差ない)。

→ 現状維持 (c) でほぼ OK だが、 将来 escape-analysis 系の最適化を
入れるなら (b) に踏み込む価値。

### A4. node_call_N の args は @child 化されていない [P2: 設計検討]

現在の node_call_1/2/3 は body 内で BARUBY_EVAL_ARG で arg を evaluate:

```c
for (uint32_t i = 0; i < locals_cnt; i++) sp[i] = 0;
sp[0] = UNWRAP(BARUBY_EVAL_ARG(c, a0, sp + locals_cnt));
sp[1] = UNWRAP(BARUBY_EVAL_ARG(c, a1, sp + locals_cnt));
sp[2] = UNWRAP(BARUBY_EVAL_ARG(c, a2, sp + locals_cnt));
```

これを `VALUE a0@child, VALUE a1@child, VALUE a2@child` に変換できれば
body は:
```c
for (uint32_t i = N; i < locals_cnt; i++) sp[i] = 0;
return RESULT_OK(EVAL(c, cc->body, sp, sp + locals_cnt).value);
```
(args は DISPATCH によって sp[0..N-1] に既にあり)。

複雑な相互作用:
- slowpath は serial mismatch 時に呼ばれる。 現状 args は body 内で
  evaluate されるので serial check 失敗 → slowpath で再 evaluate。
  @child 化すると args は DISPATCH で先に evaluate される。 副作用が
  あれば順序 / 数 が変わる。
- 言語仕様上、 method redefinition 時の引数評価は「常に 1 度」 が正解
  なので、 @child で先に評価する方が semantic に正しい (現状の二重
  評価が semantic violation)。

→ @child 化が望ましい。 ただし call_N の sp pattern が独特 (sp +
locals_cnt を渡す) なので慎重に。 別 iter で取り組む。

### A5. AOT mode で snapshot 戦略の最適選択は perf 仮説のみ [P3: 計測強化]

「sp[] が AOT で勝つ」 のは matrix data から事実だが、 内部メカニズム
は仮説 (gcc が `sp + N` static offset を SROA できる、 4-arg dispatcher
の方が aliasing 解析しやすい、 など)。 perf record + 生成 assembly の
diff で裏付けが欲しい。

裏付けが取れたら ASTroGen の docs に `@child` 機構の選択指針として
追記したい。

### A6. node_seq の head 値は本当に discard できる? [P3: 設計検討]

現在 `(void)UNWRAP(EVAL_ARG(c, head))` でわざわざ UNWRAP していて、
state != NORMAL なら early return する (control flow を伝搬する)。
これは正しいが、 head が「明らかに副作用 only で control flow を
持たない」 と分かれば UNWRAP 不要。

例: `head = node_num(3)` のような sub-expression 列は副作用ゼロ。
parser 側で「pure / impure」 を区別して emit すれば、 純粋 head は
single ガード無しで skip できる。 細かい win だが seq tree が深い
ASTで地味に効く。

### A7. baruby_precise の sp scan 範囲が依然動的 [P2: 設計検討]

GC root scan は `c->env..c->sp` を毎回走る。 c->sp は alloc 前に
sp_top で update。 これだと alloc 毎に「sp_top 受取り → c->sp 更新 →
scan」 のオーバーヘッドが残る。

代替: sp_top を gcc が register に保持しつつ、 alloc safepoint だけで
c->sp に書く設計。 既に近い形だが、 sp_top 引数の取り回しが framework
を貫いていて、 全 dispatcher が 4-arg なのが影響。

→ snapshot 機構 (`@child`) と root-set 機構の分離をきれいにできれば
更に最適化余地。

### A8. parser の `body_locals = max_cnt` 修正は over-allocate ぎみ [P3]

修正前: `body_locals = n->locals.size` (declared locals のみ)
修正後: `body_locals = max_cnt` (declared + nested call slots + binop reserves)

ackermann のような nested call が深い関数で max_cnt は declared
locals の数倍に膨れる。 frame size が大きくなる → cache 効率悪化 / GC
scan 範囲拡大。

理想は「declared + arg-slot 高水位線」 でなく「declared + 実際の
nested @child 仕掛けが必要とする slot」 を計算したい。 parser 側に
@child 用 reserve の concept を入れる方向性。 また `for sp[i] = 0` の
init コストも max_cnt 比例で増えている。

## B. 性能向上提案 (実装容易さ × 期待効果 で並び替え)

### B1. 【容易・中効果】 `callee_sp safety guard` の除去

A2 と同じ。 parser fix で本来不要になったので削る。 期待: hot path で
1 cmp + cmov 削減、 1-2% improvement on call-heavy bench (fib, ackermann)。
ベンチで oracle 全 pass 確認後 commit。

### B2. 【容易・小効果】 perf.md / 関連 docs の `iter 53` 数値を iter 58 で全 refresh

既に plain mode は更新済。 AOT matrix は再実行が必要。 ベンチ結果が
古いままだと判断ミスを誘発するので docs 健康のため refresh。

### B3. 【中規模・大効果】 node_call_N の args を @child 化

A4 と同じ。 期待: SD で args を register 越し inline 可能になり、 call
heavy bench (fib, ackermann, chain20/40, gcd, json_parse) で 5〜15%
improvement の見込み。 ただし slowpath 連携を慎重に書き直す必要。

### B4. 【容易・観測】 cons_list libgc +16% 退化の原因追跡

A1 と同じ。 perf record + flamegraph で hot 関数を特定。 仮説 (1)(2)(3)
のどれが真かを切り分けると、 fix が見えるかも。

### B5. 【中規模・大効果】 baruby_precise に @child 全 SD で「snapshot 位置 = caller の事前 reserve slot」 を渡す

現在は DISPATCH が独立に sp[0..N-1] に snapshot する。 これを caller が
事前に reserve した slot に書き込ませれば、 SD inline 時に gcc が
caller の register 経由で値を渡せる。

```c
// 現状の SD
sp[0] = UNWRAP(SD_<child_h>(c, n->u.node_add.lv, fp, sp + 0));

// 提案
register VALUE _c0;
_c0 = UNWRAP(SD_<child_h>(c, n->u.node_add.lv, fp, sp + 0));
sp[0] = _c0;  // store (precise GC root scan のため必要)
// EVAL_node_add は _c0 / sp[0] のどちらでも読める
```

GC スキャンには sp[i] が必要だが、 register 中継で hot path の load
は省ける。 LTO inline が深い場合 store が dead store になる可能性も。
要 assembly 確認。

### B6. 【大規模・大効果】 真 SSA-based AOT pass の導入

現在の AOT は SD chain の `static inline` で gcc に任せている。 LTO で
inline + SROA + DCE を期待する pattern。 これは効くが、 baruby 固有の
意味 (VAL2INT / IS_INT の semantics, alloc safety) を gcc は知らない
ので最適化が止まる箇所がある (例: 連続 INT2VAL/VAL2INT の互いに
打ち消し合い、 GC barrier の不要な発火、 など)。

ASTroGen が AST → 中間 IR (e.g., MLIR-ish) を生成して domain-specific
pass を適用してから C を吐けば、 さらに 2-5× の AOT 性能を引き出せる。
ただし大規模 framework 変更。

### B7. 【容易・小効果】 `aro_gc_alloc` インライン化の徹底

iter 43-45 で cold-path split を入れて size_class lookup + bump 部分は
inline 化できた。 まだ `aro_gc_alloc_byte` の inline 化は限定的 (todo.md
にエントリあり)。 各 backend で hot path 部 (bump + size_class) を
single header に出してしまうと、 caller 側で `aro_gc_alloc(OBJ_ARRAY, 24,
sp)` の特化形が完全 inline する。

### B8. 【容易・小効果】 `node_str_lit` の rodata 化

現在は per-eval で `baruby_str_new(bytes, len, sp)` を呼んで新たな
BaString + bytes を heap alloc。 string literal は不変なので、 一度
作って NODE struct に value を焼く intern pool ができれば call 回数
削減。

```c
NODE_DEF
node_str_lit(... const char *bytes, uint32_t len, VALUE *cached@once)
{
    if (*cached == 0) {
        *cached = baruby_str_new(bytes, len, sp);
        /* register as GC root for libgc; for precise GC, intern in a
         * permanent region. */
    }
    return RESULT_OK(*cached);
}
```

期待: string-heavy bench (tokenize, string_concat) で per-iter の
str_new コスト削減 (現状 string_concat_dyn の chunk 構築でも str_new
が hot)。

### B9. 【中規模・中効果】 `node_call_aget` を type-specialized variant に

現在 `node_call_aget` は `IS_ARY(recv)` と `IS_STR(recv)` の type test
を毎回。 PG 情報を使って「ほぼ常に Array」 と分かれば
`node_call_aget_ary` バリアントを emit して type guard 1 つに減らせる。

ASTroGen の SPECIALIZE phase で型観測を取り込めば、 PGSD bake 時に
variant choice ができる。 既に PG mode (node_pg_call) があるので
延長で実装可能。

### B10. 【大規模・大効果】 inlining barrier (`@noinline`) を最小化

baruby_precise/node.def で `@noinline` 指定がついている node を確認:
```
NODE_DEF @noinline
node_def(...)
```

`node_def` は @noinline。 これは「method 定義時のみ実行、 hot path で
ない」 ので spec で AOT inline しない方が SD bloat を避けられる、 と
いう判断。 でも他の cold path (slowpath とか string conversion とか)
も明示しないと SD chain に紛れ込む可能性。

逆に常に inline 強制している node (`@always_inline`) もある。 control
flow node (if, while, seq) は必須。 これらが間違って外れると LTO で
SD chain が崩壊する。 明示的な指定の audit が定期的に必要。

### B11. 【容易・中効果】 baruby (libgc) の `BaArray.bytes` SSO 拡大検討

iter 53 で `BSTR_SSO_MAX = 7` (BaString 24B 維持) を選んだが、 libgc
側だけ `BSTR_SSO_MAX = 15` (BaString 32B) にしても問題ない可能性が
高い。 libgc は size class が 16B 単位なので 24→32B でも次の size
class に乗ることが多い。

baruby_precise では fib_pair で +8% regress したが、 libgc では int
arith は heap を触らない (fixnum tagging で済む) ので影響無いはず。
A/B で確認する価値。

### B12. 【中規模・中効果】 baruby_precise に "register-resident sp_top" を導入

現状 dispatcher は (c, n, fp, sp) を引数で受け、 sp は register 経由。
ただ alloc 時に `c->sp = sp_top` を memory に書く必要 (root scan の
ため)。 これが毎 alloc コスト。

代替: c->sp を CPU register (Linux x86_64 で r15 など callee-saved 確保)
に pin、 alloc は register 越しに root range を確定。 ABI に介入する
非標準テクニックだが、 VM 系では珍しくない (e.g. Ruby JIT)。 5-10%
の improvement の可能性。

## C. アーキテクチャ的整理

### C1. ASTroGen の per-language hook の現状

iter 58 で追加された hook:
- `child_storage_decl(slot)` — snapshot の宣言
- `child_storage_expr(slot)` — snapshot の lvalue / 引数 expr
- `child_dispatch_args(slot, field)` — 子 dispatcher 呼び出しの引数

そして既存:
- `common_param_count` — dispatcher 引数数 (3 or 4)
- `result_type` — RESULT or VALUE
- `Operand.build_specializer` — per-operand-type の SD emit
- `Operand.hash_call`, `build_dumper` — per-operand-type hash / dump

per-language hook の数が増えてきた。 整理して `LanguageProfile` クラス
にまとめると見通しが良いかも (将来 calc, pascalast 等にも適用したい場合)。

### C2. 19 個の bench は何を測っているか

iter 36-58 で追加された bench 群:

| カテゴリ | bench | 主な軸 |
|----------|-------|--------|
| AST eval pattern | ast_eval | interpreter loop |
| 整数 / 制御 | fib_pair, fannkuch, sieve, nqueens, list_sort, life | mutator |
| Array alloc heavy | binary_trees, cons_list, list_alloc, gc_combined | GC alloc + sweep |
| String alloc heavy | string_concat, string_concat_dyn, substr_churn, tokenize, json_parse | string ops + bytes alloc |
| Generational stress | dll_walk, hash_chain, remset_pressure, interp_calc | WB + remset + gen |

カバレッジは広い。 ただし最近の追加 (json_parse, tokenize) は string +
小 array に偏っているので、 「大規模リストの fold/reduce」 や「dict
lookup 集中型」 等のパターンがやや薄い。 補完を検討。

### C3. GC backend 16 種は維持コスト vs 学術価値

iter 36-50 で baruby_precise の GC backend を 16 種まで増やした。 各
backend は教育用に大きな価値があるが、 maintenance cost (新 NODE
追加時に各 backend の scan を更新する必要、 iter 58 でも 15 backend
更新) も大きい。

`gc_runtime.md` で各 backend の特徴を整理しているが、 もう少し「どの
backend が現実の言語実装に対応するか」 を明示すると教育的価値が
上がる。 例:

- `mark_gen` = CRuby のような sticky mark&sweep + gen
- `copy_gen` = SmallTalk / Lisp 系の semi-space
- `immix_gen` = JVM Z, Shenandoah の前駆 (mark-region)
- `mark_freelist` = malloc-style allocator (perf比較用)

### C4. AOT / PG / JIT の役割分担

- AOT (`-c`): SPECIALIZE で SD を bake、 程よく inline。 cross-SD で
  framework の優位性が出る。
- PG (`-p`): hopt hash で profile-aware SD (PGSD)、 sp_body 直接 call
  で速い。 でも cc 更新やや複雑。
- JIT (`-j`): astro_jit.c で別 process がコンパイル、 IR 経由。 baruby
  ではまだ wired off (post-fork で停止状態と comment あり)。

JIT を最終ゴールにするなら、 IR を **AOT と JIT で共通の中間表現** に
してしまう設計が良い。 現状は AOT は C source 直、 JIT は別 IR。
統合できれば PGO 情報の活用や cross-mode tuning が一元化できる。

## F. iter 58 までの「設計の正解」 として確定したこと

- **`@child` の per-language hook** (`child_storage_*` + `child_dispatch_args`)
  は **明確に正しい設計**。 plain/AOT で snapshot 戦略の勝者が逆転する
  事実を、 hook 経由で吸収できている。
- **precise GC + sp[] root scan** は AOT で最適、 conservative GC +
  C-local は plain で最適。 これは ASTro が「同じ AST framework 上で
  異なる GC 戦略を並走」 できる強みの実証。
- **`@nogc` / strict-arg / ANF style** は @child 機構として実装済 (sample/
