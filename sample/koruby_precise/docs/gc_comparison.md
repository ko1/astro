## 【2026-06-24】静音マシン (load ~0.4) で interp / AOT / GC時間 を再計測 (信頼値)

§下の 2026-06-23 初回計測は load 24〜30 で elapsed/fps がノイズ床 ±30〜40% に埋もれ
backend 間を分離できなかった (alloc/gc_count の決定論値のみ信頼)。idle なマシンで
**interp(--plain) と AOT(--compiled-only warm) の両方 + GC時間** を取り直した。全 run
checksum 一致。raw: `bench-report/20260624-021430-gc-full.tsv`。
再現: `tools/gc_full_compare.sh "<backends>" "<benches>"`。

**ベンチ選定基準**: GC を起こさない (alloc≒0) ベンチは全 backend で同一なので除外。
**copy backend で gc_count ≥ 3** のベンチ 20 本のみ対象 (collection が複数回起き
per-collection コスト差が出る閾値)。残り 31 本 (fib/ackermann/nbody/while 等) は
gc_count=0 で backend 完全に無関係。各表の `(N)` は gc_count。
**`aot+compile` (cold/bake) は出さない**: bake 時間は実行時 GC backend に依存しない
(どの GC でビルドしても SD コンパイル時間はほぼ同じ) ので backend 比較軸として無意味。

### 信頼できる結論 (静音マシン, 上の表より)
- **copy_gen は retained+young churn で勝つ**: gen_gc 0.314→**0.264 (-16%)**、gcchurn -6%、
  ary -17%、strscan -13%。負荷時に埋もれていた世代別の利得が idle で顕在化。GC時間も
  copy_gen が copy の 1/10〜1/40 (例 ary 0.012→0.001、gen_gc は §raw 参照)。
- **immix は tree / 大obj / closures で僅差トップ** (binary_trees / gc_bigobj / closures /
  nesteddata)。
- **copy_gen は大obj で負ける** (gc_bigobj 0.191→0.208): 大きいオブジェクトが小 nursery 溢れ。
- **mark-sweep 系 (mark_gen / mark_compact_gen) は churn で一貫最遅** (strscan/str/strfmt/
  array_access で 1.3〜2.7×): 生存だけ触る copy/immix と違いヒープ全体を mark/sweep =
  GC時間が桁違い (例 strfmt mark_gen GC 0.21s vs copy 0.001s)。
- **default `copy` は全域で堅実** (optcarrot/str/array_access/object で最速級、どこでも最遅に
  ならない、世代別の write-barrier 負荷も大obj 劣化も無い)。**汎用 default は copy が最善**。
  世代別 (copy_gen) に替える価値があるのは「retained 集合 + 若死に churn が支配的」な
  ワークロード限定。

### (以下 2026-06-23 の初回計測 — load 高でノイズ支配、決定論値=alloc/gc_count のみ信頼)

## 計測方法

- ベンチ: `sample/rubyharness/bench/*.rb` 全 51 本 (GC stress 用に `gc_wb`=write-barrier、
  `gc_bigobj`=大オブジェクト churn を追加済)。
- `KORUBY_GC_STATS=1 --plain`、各 (bench,backend) を round-robin で 3 周、各値は 3 周の最小値。
- 全 run の出力を CRuby と一致検証 (1件を除き ok、§4 参照)。
- 再現: `make gc-compare` / `tools/gc_bench_ab.sh` / `tools/gc_report.rb`。

## ⚠️ 測定ノイズ床 — 小さい差は信用しないこと

このマシンは 16 core に対し load 24〜30 で oversubscribe している。**GC を一度も
起こさないベンチ (`gc_count=0`、§1 で gc 0) は backend が影響しようがない**のに、
backend 間で実行時間が **1.15〜1.72× (典型 ~1.35×) ばらついた**:

| 0-GC control bench | min[秒] | max[秒] | max/min |
|---|--:|--:|--:|
| ackermann | 1.55 | 1.99 | 1.28× |
| fib | 0.78 | 1.15 | 1.47× |
| method_call | 1.79 | 2.57 | 1.43× |
| nbody | 1.02 | 1.35 | 1.33× |
| kwargs | 0.62 | 1.06 | 1.72× |
| while | 1.72 | 2.12 | 1.23× |

→ **実行時間 (§2) の backend 差が ~1.4× 以内なら、それは GC ではなく測定ノイズ。**
「copy_gen が 5〜10% 速い」級の差は**全部ノイズに埋もれている**ので主張できない。
信用できるのは (a) 決定論的な alloc/gc_count (§1)、(b) ノイズ床を大きく超える差
— 特に GC 時間 (§3) で mark 系が copy の数十〜100倍という桁違いの差。
**集約値 (geomean) は出さない**: ノイズの geomean は精密な数字に見えて無意味だから。
真に小さい効果を測るには load の低い静かなマシンが要る (今は数時間ずっと高負荷)。

## 結論 (このマシン負荷で言えること / 言えないこと)

**決定論的に言えること:**
- 51 本中 GC を起こすのは 24 本のみ。残り 27 本は alloc≒0 / gc 0 回で **backend 完全に
  無関係** (§1)。
- churn 系 (strfmt/gcchurn/str/ary/gen_gc 等) で **mark-sweep 系 (mark/mark_gen/
  mark_compact) の GC 時間は copy の数十〜100倍** (§3、strfmt: copy 0.003s vs
  mark_compact 0.727s = 240×)。コピー/immix 系は生存オブジェクトのみ触るが mark-sweep は
  ヒープ全体を mark/sweep するため、若くして死ぬゴミが多いと圧倒的に不利。これは
  ノイズ床を遥かに超える確実な差。
- copy_gen は copy より GC 時間が小さい (gen_gc: copy 0.141s vs copy_gen 0.042s)。
  generational が若死にゴミの minor 回収で効くのは確か。

**このノイズ床では言えないこと:**
- 実行時間 (§2) で copy vs copy_gen vs immix の優劣 (差が ~1.4× 以内 = ノイズ床内)。
  「世代別が総時間 10% 速い」級は今の load では証明不能。静かなマシンでの再測が必要。

**バグ (§5, 修正済):** `mark_compact_gen` は bignum で core dump していた
(fold_young の finalize-list 昇格漏れ) → 2026-06-23 修正。

**実務的結論:** default の `copy` を変える明確な根拠は (この測定では) ない。churn 系で
mark-sweep 系を避けるべきなのは確実 (GC 時間が桁違い)。最重要なのは
**GC 選択より mutator 高速化** (optcarrot で実証済: GC は実行時間の 1〜4%、
docs/... の Integer#[]/Hash#[] inline 等)。
