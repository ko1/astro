## 型検査の未カバー（健全性を完全には保証しない箇所）

現状の検査器は仕様 §5.2 の主要規則（式の型推論・代入互換・arity・戻り型・クラス構造）を
実装するが、以下は未実装。妥当なプログラムは正しく動くが、一部の不正プログラムを取り逃す:

- **全経路 return**: `int`/`bool`/`str` を返す関数で「全実行経路が return を含む」検査。
- **暗黙継承変数への代入禁止**: 囲みスコープから read-only に見える変数への代入の禁止
  （`var-read` の関数型禁止、read-only 検査）。
- **`[<None>]` の複数代入禁止**（`multi-assign-stmt` の `T0 != [<None>]` 制約）。
- **メソッドオーバーライドのシグネチャ一致**（第1引数以外の型・戻り型が厳密一致）。
- **属性の再定義禁止 / メソッドの同クラス内再定義禁止 / 第1仮引数が定義クラス型**。
- **名前の重複・シャドウ規則**（クラス名は変数/関数と衝突不可、等）の網羅。
- エラーメッセージは reference checker と非互換（テストは「型エラーで拒否されるか」で検証）。

## 言語機能

- **整数オーバーフロー**: 仕様上 UB。実装は機械語幅（実質 64bit）で計算するので、32bit を
  超える領域では Python（bignum）と挙動が異なる。差分テストは範囲内に限定。
- 文字列エスケープは `\" \\ \t \n` のみ（仕様もこの4種）。

## フレームワーク連携

- **`--build` と関数/クラス定義**: 関数・クラスはパース時にグローバル登録するため、AST のみを
  埋め込む `--build` 単体 exe では失われる。関数定義を含まないプログラムのみ対応
  （cf. abc/docs/todo.md と同じ構造的制約）。関数記述子の直列化が必要。
- PG モード未配線。

## 性能（詳細は [perf.md](perf.md)）

- 関数呼び出しごとに GC 環境フレームを確保し、引数/ローカルを名前ハッシュで登録するため
  call 主体のコード（tak/fib）が CPython より遅い。**名前をスロット番号に解決**して
  per-call ハッシュを廃せば改善見込み（abc の fixnum 化に相当する次の一手）。
- AOT 特殊化は ~0.95×（dispatch は減るが env/helper 呼び出しが残る）。
